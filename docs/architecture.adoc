This document describes emuLib with the https://c4model.com/[C4 model] and
defines its package boundaries. emuLib is one Java library used by two different
consumer groups: the emuStudio main application and emuStudio plugins.

== Architectural rules

Packages under `net.emustudio.emulib` are public API by default. Packages named
`internal` explicitly mark private API that must not be used by emuLib consumers,
including plugins and the emuStudio application.

The public API is divided by ownership and direction, not merely by technical
topic:

[cols="1,2,2",options="header"]
|===
| Namespace | Implemented or owned by | Used by

| `plugin`
| Plugins and emuLib
| Plugins implement contracts and may reuse base classes; emuStudio loads and
  drives plugin roots

| `application`
| emuStudio main application
| Plugins call host services supplied through `ApplicationApi`

| `net.emustudio.emulib`
| emuLib
| General-purpose types used by plugins, emuStudio, and other emuLib APIs

| `io`, `ui`, `audio`, `recording`
| emuLib
| File-format, reusable Swing, audio playback, and recording APIs used where needed
|===

`plugin` and `application` are two sides of the same boundary. The
former is the plugin SPI: plugins implement it and emuStudio calls it. The latter
is the host API: emuStudio implements it and plugins call it. General-purpose,
I/O, and UI types are public APIs without defining another lifecycle boundary.

== Level 1 - System context

emuLib sits at the compile-time and runtime boundary between the emuStudio main
application and independently developed plugins. It is a library, not a runnable
system.

=== Context responsibilities

Plugin developers::
Implement one plugin root type (`CPU`, `Memory`, `Compiler`, or `Device`), expose
typed `Context` interfaces where needed, and optionally reuse base classes and
helpers.

emuStudio developers::
Discover and instantiate plugin roots, implement `ApplicationApi`,
`ContextPool`, settings, dialogs, GUI, and execution services, then drive
the plugin lifecycle.

emuLib::
Defines the stable types crossing that boundary. It does not load plugins or
provide the main application's service implementations.

== Level 2 - Container

emuLib is published as one `emulib.jar` (`net.emustudio:emulib`) targeting Java
11 bytecode. It runs in the same JVM as the host application and loaded plugin
JARs.

=== Container constraints

* emuLib remains one artifact; the separation is expressed through packages.
* SLF4J, JCIP annotations, and ANTLR are `compileOnly`. The consuming runtime
  supplies them when the corresponding feature is used.
* JCodec is an implementation dependency used for media recording.
* The main application and plugins share the same public emuLib types at runtime.

`net.emustudio.emulib` or its domain and role subpackages. Packages named `internal`

== Level 4 - Code

=== Plugin side: implemented by plugins

[plantuml,c4-l4-plugin,svg]
....
@startuml
title Code - plugin API

package "plugin" {
  interface Plugin
  interface CPU
  interface Memory
  interface Compiler
  interface Device
  interface Context

  Plugin <|-- CPU
  Plugin <|-- Memory
  Plugin <|-- Compiler
  Plugin <|-- Device

  abstract class AbstractCPU
  abstract class AbstractCompiler
  abstract class AbstractPlugin

  CPU <|.. AbstractCPU
  Compiler <|.. AbstractCompiler
  Plugin <|.. AbstractPlugin
}

note bottom
  Plugin root constructor:
  (long pluginId, ApplicationApi api, PluginSettings settings)
end note
@enduml
....

The main application discovers one root class per plugin and calls the `Plugin`
lifecycle. Plugin implementations may implement the contracts directly or extend
the optional abstract bases.

=== Application side: implemented by emuStudio

[plantuml,c4-l4-application,svg]
....
@startuml
title Code - application API exposed to plugins

  +getContextPool() : ContextPool
  +getDialogs() : Dialogs
  +getGUI() : GUI

interface PluginSettings

  +snapshot() : Snapshot
  +subscribe(listener) : Subscription

}
class MemoryAnnotations

ApplicationApi --> ContextPool
ApplicationApi --> Dialogs
ApplicationApi --> GUI
ApplicationApi --> ExecutionState
ApplicationApi --> MemoryAnnotations

note right of ApplicationApi
  emuStudio implements these contracts.
  Each plugin receives them through its constructor.
end note
@enduml
....

`ExecutionState` keeps a stable host-owned publication stream available before a
machine is initialized. Views read snapshots, subscribe to changes, and submit
live edits with `update`. Paused-only command validation stays inside the host.
The host installs a CPU boundary callback through `Debugging.onBoundary`; CPU
engines invoke it before every outer semantic step even without an active debug
observer. Queue draining therefore stays outside the view-facing state API.

=== Context exchange

Contexts are the only plugin-to-plugin API. A plugin registers a context during
construction; another plugin resolves it during `initialize()`. `ContextPool` is
implemented by emuStudio but operates on plugin-owned context types.

[plantuml,c4-l4-context,svg]
....
@startuml
title Code - typed context exchange

interface Context <<@PluginContext>>
interface CPUContext
interface "MemoryContext<CellType>" as MemoryContext
interface "DeviceContext<DataType>" as DeviceContext
interface ContextPool

Context <|-- CPUContext
Context <|-- MemoryContext
Context <|-- DeviceContext
ContextPool o--> "*" Context : registers and resolves

note right of ContextPool
  Registration key: context interface
  Owner/permission key: plugin ID
  Multiple implementations: 0-based index
end note
@enduml
....

== Cross-cutting concerns

API boundary::
Packages are public API by default. Packages named `internal` explicitly mark
private API that must not be used by emuLib consumers, including plugins and the
emuStudio application.

Concurrency::
`Context` is documented as thread-safe. `AbstractCPU` serializes CPU execution
and state transitions. `ReadWriteLockSupport` is a public utility for consumers
that need guarded shared state.

Headless operation::
`ApplicationApi.UNAVAILABLE` and `PluginSettings.UNAVAILABLE` let plugin code run
without a full emuStudio host where supported. GUI-related interfaces remain
host-owned contracts.

Extensibility::
New inter-plugin capabilities should normally be expressed as typed context
interfaces annotated with `@PluginContext`, avoiding direct plugin
implementation dependencies.
